# Plan: Formalize OpenApoc Live-Test Harness (Deterministic)

Status: Draft
Branch: ci/1637-live-test-harness
Source of truth: live-test/ARCHITECTURE.md (wins on conflict with live-test/README.md)

## Objective

Turn the current AI-agent-driving prototype (socket + full command parser living in `framework/harness.h/cpp`, command interpretation leaking into `forms/harness_actions.cpp` / `harness_ui.cpp`) into the three-layer design in ARCHITECTURE.md: `framework/` exposes only a neutral per-frame hook and generic primitives, `game/harness/` owns the protocol/probe surface and installs itself via that hook, and `live-test/` is an external, deterministic QA runner that drives real game builds under Xvfb/software-GL/dummy-audio, scripts scenarios (e2e or from save fixtures), asserts against a small stable probe contract, and emits machine-readable artifacts. Runs must work from a clean VM (Vagrant) or container (Docker) in local dev and CI. Prototype code is treated as a design reference, not code to patch in place; it gets rewritten, not extended.

## Canonical Probe Contract (locked before Phase 2 implementation)

ARCHITECTURE.md and README.md list overlapping but non-identical probes. Merged, minimal starting set (grow only when a concrete test needs a new one):

```
stage.name
frame.number (diagnostic-only: reported in result.json and readable via GS, never valid inside an equals assertion, since the frame a command lands on is socket/wall-clock dependent)
gamestate.current_city.exists
gamestate.player.balance
log.errors
log.warnings
```

`stage.detail` is deferred to the backlog below rather than locked into v1: no stage in the codebase overrides `Stage::harnessDetail` (the default returns an empty string), so locking it now would lock a probe that is vacuous for every stage at lock time. It moves to the backlog and gets implemented for a specific stage only when a Phase 2+ script actually needs that stage's detail.

`save.digest` is also deferred to the backlog below rather than locked into v1: a digest of raw save bytes is not deterministic (the save manifest embeds a wall-clock `save_date` and the zip container carries its own metadata). When a later phase needs it, define it as a hash of the canonicalized serialized game-state content, explicitly excluding the manifest `save_date` field and all zip container metadata (fixed entry order, zeroed timestamps).

Deferred backlog (documented, not implemented yet): `stage.detail` (see rationale above), `save.digest` (see definition above), `stage.stack`, `gamestate.current_city.id`, `gamestate.current_base.name`, `gamestate.messages.count`, `ui.visible_form`, `ui.focused_control`, `screenshot.hash`. These get added later, one at a time, when a specific test needs them (and, for `stage.detail`, when the consuming stage gets its `harnessDetail` override implemented alongside it), and get appended to the same contract doc in `game/harness/harness_protocol.h`.

Command surface is fixed to the ARCHITECTURE.md list (`STATUS`, `HELP`, `QUIT`, `CLICK`, `MOVE`, `DOWN`, `UP`, `SCROLL`, `KEY`, `KEYDOWN`, `KEYUP`, `TEXT`, `SCREENSHOT`, `SAVE`, `RESIZE`, `UI`, `CONTROLS`, `CONTROL`, `GS`, `ACTION`). No new commands beyond this list without a plan revision. README.md's own command list is missing `KEYDOWN`/`KEYUP`/`ACTION`; reconciling it to this fixed list is a Phase 2 task (see below).

## Determinism Contract (decided up front, documented in harness_protocol.h)

- `Game.ASyncLoading=false`, `Config.Save=false`, `Config.Read=false`, `Game.SkipIntro=true` (`Config.Read` defaults to true and would otherwise silently load the developer's own `settings.conf` from the PHYSFS pref dir on a local run, a local-vs-CI drift source a clean-VM/CI run never hits since no such file exists there)
- `Framework.TargetFPS`, `Framework.FrameLimit` set to fixed values per script
- `SDL_AUDIODRIVER=dummy` / `Framework.AudioBackends=null`
- `LIBGL_ALWAYS_SOFTWARE=1` (Mesa software GL)
- `Game.Load=<fixture path>` for save-fixture scenarios (Phase 8): the boot-time load path runs through the same async-loading screen this contract already governs, so `Game.ASyncLoading=false` still applies when loading a fixture
- RNG seeding: `OpenApoc.NewFeature.SeedRng` defaults to true and, when enabled, seeds `GameState::rng` from wall-clock time in `GameState::startGame()` (new-game path only; loading a save never reseeds). This contract mandates `OpenApoc.NewFeature.SeedRng=false` for every scripted run (CTest's `tests/test_helpers.h` already forces this for unit tests; live-test scripts must set it explicitly too). With it false, new-game runs use the default-constructed rng (seed 0), and save fixtures carry their own serialized rng state, so both paths give a fixed stream today. The remaining gap is that there is no option to pick a fixed seed other than 0, still deferred (see Out of Scope and Open Questions). Determinism is per-platform only: draws go through `std::uniform_int_distribution`, whose algorithm is implementation-defined, so a Linux (libstdc++) run and a Windows (MSVC) run of the same seed are not guaranteed to draw the same sequence. `srand(SDL_GetTicks())` at framework start is unpinned but has no `rand()` consumers found in game/forms/framework code, and the jukebox's own wall-clock-seeded shuffle rng is irrelevant under dummy audio.
- Sim pause / tick control: fixed-timestep polling alone only gives deterministic eventual state on static screens; any post-boot scenario (CityView and beyond) ticks the sim every frame from stage entry, and `CityView` hardcodes `updateSpeed(CityUpdateSpeed::Speed1)` on construction, so a pause delivered over the socket (an `ACTION` verb setting `CityUpdateSpeed::Pause`, or a first-step convention) only arrives after a socket-latency-dependent, non-reproducible number of ticks have already elapsed; it bounds but does not eliminate pre-pause tick variance, so equals-assertions on tick-sensitive state (`gamestate.player.balance`, a `SAVE`) are unsafe under a socket-delivered pause alone. The mechanism that actually gives reproducible state is a start-paused config option (stage enters already at `CityUpdateSpeed::Pause`, before the first tick), extended with a deterministic run-N-ticks-then-pause parameter (a fixed tick count, checked in the stage's own update loop each frame, that auto-re-pauses the sim once reached, never delivered or adjusted over the socket); the start-paused behaviour exists today only as a compile-time `DEBUG_START_PAUSE` block (cityview.cpp:1814-1816); Phase 8 promotes it to a runtime option and adds the run-N-ticks-then-pause half, which does not exist in any form; both are scoped as explicit new engine work in Phase 8's files touched (see that phase). Phase 8's fixture-generation task depends on this run-N-ticks-then-pause mechanism specifically (start paused, advance exactly N engine-counted ticks, auto-pause again, then `SAVE`), not on the socket-delivered pause, so a fixture that needs elapsed sim time never relies on socket-latency-dependent timing. Battle stages use their own `BattleUpdateSpeed` enum (`CityUpdateSpeed::Pause` has no effect there); a fixture whose save contains a battle boots straight into `BattleView` via `Game.Load`, so Phase 8's v1 fixtures are restricted to city scenarios unless a `BattleUpdateSpeed::Pause` equivalent is added under the same start-paused mechanism.
- Frame stepping: fixed timestep + wait-until-probe polling for v1. Manual frame stepping (engine-driven single-frame advance) is explicitly deferred unless fixed-timestep proves flaky in practice (Pattern: hook before poll, prove the simple thing first)

## Acceptance Criteria (whole effort)

- [ ] `framework/` contains no game-aware command parsing or protocol code; only generic hooks/primitives (the frame hook, `pushEvent`, screenshot, resize, stage/status access, quit, per-level log counters, and the harness-gated suppression of the modal SDL dialog logger) and the `Framework.Harness.*` option definitions
- [ ] All socket + protocol + command parsing lives in `game/harness/` (`harness_api.h/cpp`, `harness_protocol.h/cpp`)
- [ ] `forms/` exposes only a neutral visible-form observation hook; no command/action interpretation remains in `forms/harness_actions.cpp` or `harness_ui.cpp` (files removed or fully gutted)
- [ ] `game/main.cpp` calls `HarnessApi::install(*fw)` before `fw->run()`, gated by `Framework.Harness.Enable` (default off)
- [ ] Locked 6-probe contract implemented and documented as a stable compatibility surface; `STATUS` reply includes an integer protocol version
- [ ] `live-test/bin/run` boots the real game under Xvfb in the clean Vagrant env using only `cd_minimal.iso`, runs one smoke scenario, and exits non-zero on failure
- [ ] Smoke test (boot to MainMenu via `STATUS`, `log.errors == 0`, nonblank screenshot, clean `QUIT`) passes locally and produces `result.json`
- [ ] CTest parser unit tests exist against the new `game/harness/harness_protocol.cpp` grammar (created in Phase 2, coverage gaps ported and old `tests/test_harness.cpp` removed in Phase 4)
- [ ] CI job runs the smoke test on the fork's GitHub Actions by reusing the existing build job's binary, separate from the existing AppVeyor Windows build, and the AppVeyor Windows build itself stays green throughout
- [ ] No full retail CD data is downloaded, mounted-by-default, or committed anywhere in CI; only `cd_minimal.iso` is used in CI, checksum-verified
- [ ] JSON scenario runner (Phase 7) executes at least one committed script (`live-test/scripts/boot-main-menu.json`) beyond the Phase 5 hardcoded path, with both `{"probe": equals}` and `{"artifact": nonblank}` assertion kinds working
- [ ] Docker variant (Phase 8) reproduces the same pass/fail result as the CI job for the same script
- [ ] Suite-level selection (Phase 7) runs a named suite, writes a per-script `result.json` for each plus a suite summary, and exits non-zero if any script fails
- [ ] At least one save-fixture scenario and at least one UI-driven e2e flow (Phase 8) pass locally

## Out of Scope

- Pixel-perfect screenshot comparison (nonblank check only, for now)
- Manual/engine-driven single-frame stepping (deferred, not ruled out)
- Full assertion DSL beyond `{"probe": equals}` and `{"artifact": nonblank}` before the smoke test is green
- A fixed-seed-value RNG option (flagged as a gap in the Determinism Contract, not built here; forcing `SeedRng=false` is in scope, adding a new seed-value option is not)
- AI-agent-driving use case from the current prototype (explicitly being replaced by deterministic scripted testing)
- Windows harness runtime support (AppVeyor stays build-only; the harness code must still compile and link on MSVC, since AppVeyor compiles every source file including the new module's duplicated-then-consolidated socket code)

## Risks

- **Determinism flakiness**: async subsystems (audio thread, texture/asset loading) may not be fully covered by `Game.ASyncLoading=false`, causing intermittent probe/log-cleanliness failures. Mitigation: start with generous timeouts and `until`-polling rather than fixed sleeps; treat any flaky smoke run as a blocking bug before adding more scripts.
- **CI runtime budget**: a from-scratch rebuild (gcc-14, Release, no ccache) is tens of minutes even on the standard hosted runner (public-repo `ubuntu-24.04` runners are 4 vCPU since Jan 2024, not the older 2-core private-repo figure), not just "minutes added". Mitigation: the Phase 6 smoke job runs `needs: build` and reuses the existing build job's compiled binary via `actions/upload-artifact`/`download-artifact`, and reuses the checksum-verified `cd_minimal.iso` via `actions/cache` keyed on its hash (see Phase 6), instead of rebuilding from scratch or re-downloading. Step timeouts are environment-scaled (a runner-config timeout multiplier, set higher in CI than locally), since software-GL (llvmpipe) on the shared runner can render well below `Framework.TargetFPS`.
- **Game data licensing**: `cd_minimal.iso` is already fetched in the existing `cmake.yml` CI job and is fine to keep using, now pinned to a checksum and cached (Phase 6). Full retail CD data must never be committed to the repo or fetched automatically in CI; save-fixture and e2e tests that need more than `cd_minimal.iso` run locally only, with data mounted outside the repo (matches README's "never committed" guidance). This also covers the new artifact class Phase 8 introduces: a save fixture serializes `GameState`, and a save generated purely from `cd_minimal.iso` content (already the CI-fetched, redistributable exception to the "never committed" rule) is treated as committable, pending maintainer confirmation of `cd_minimal.iso`'s redistribution provenance; every other fixture (anything needing more than `cd_minimal.iso`) is either generated at test-setup time by its own generator script or stored outside the repo, never committed (Phase 8 decision, see that phase's fixture-storage task).
- **Env drift between Vagrant, Docker, and bare CI runner**: software-GL/Mesa behavior differences could make "nonblank screenshot" pass locally and flake in CI, or vice versa; today the Vagrantfile also builds with a different compiler and build type than CI (gcc-14/Release), and the two also source CMake itself differently (CI relies on the `ubuntu-24.04` runner image's preinstalled CMake to shadow its own `apt install cmake`, since noble's apt CMake is 3.28 against the project's `CMAKE_MINIMUM_REQUIRED(VERSION 3.30)`; the Vagrantfile instead pip-installs `cmake>=3.30` into a venv), a third drift source. Mitigation: keep the assertion coarse (nonblank, not pixel-hash) until the environments are proven consistent, and extract one shared provisioning/build script (Phase 5) consumed by both the Vagrantfile and the Actions workflow, owning CMake provisioning explicitly (pip/venv `cmake>=3.30` or the Kitware apt repo, the same mechanism in both environments) so compiler/build-type/CMake-version drift is structural to fix, not accidental.
- **Windows build regression (ws2_32/Winsock ownership move)**: this branch's own HEAD commit exists to fix a Windows link failure in the current socket code (`ws2_32` is linked because `framework/harness.cpp` holds the winsock includes, `WSAStartup`, and `WSACleanup`); moving that code into `game/harness/` while the prototype path is still active would strand the prototype without a socket on Windows, or (if only duplicated) leave dead code, so removal must wait until the prototype itself is deleted. Mitigation: Phase 2 duplicates the winsock includes/`WSAStartup`/`WSACleanup`/`ws2_32` link onto the new `game/harness/` target while leaving `framework/harness.cpp` and `framework/CMakeLists.txt`'s existing `ws2_32` link untouched; Phase 4 removes framework's copies in the same commit that deletes `framework/harness.cpp` (see those phases' acceptance criteria). Verification: AppVeyor never builds this branch as pushed (`appveyor.yml`'s `branches: only` is `master`/`release.*`), so "stays green" is checked either via an open PR from this branch to the fork's `master` (AppVeyor builds every push to an open PR) or a fork-side `appveyor.yml` branch-filter addition, reverted before the branch is upstreamed; checked at Phase 1, Phase 2, Phase 3, Phase 4, and Phase 8 (every phase that touches MSVC-compiled code; see those phases' acceptance criteria).
- **Protocol/probe churn**: locking the command list and a 6-probe contract early is deliberate, but a future test may need a probe or command not on the list. Mitigation: `STATUS` reply carries a protocol version int, implemented as a Phase 2 deliverable (not just a recommendation), so scripts can detect a mismatch instead of silently misinterpreting output.
- **Refactor breaking existing coverage**: moving the parser out of `framework/harness.cpp` risks silently dropping test coverage if the existing `tests/test_harness.cpp` suite is coupled to old internals rather than to the command grammar. Mitigation: the new grammar gets its own CTest target as soon as the parser exists (Phase 2), coexisting with the old test until Phase 4 deletes it; keep CTest green throughout, don't delete the old test until the new one covers the same grammar.
- **Upstream merge / PR-size exposure**: this plan touches `Framework::run`'s main loop, `Form`'s constructor, top-level `CMakeLists.txt`, and `game/main.cpp`, the same files upstream churn is likely to collide with, and the branch is currently ahead-only of `origin/master`. Mitigation: merge `origin/master` at each phase boundary and keep CTest green after each sync; scope the eventual upstream PR to Phases 1-4 only (the engine refactor, hook, and tests), keeping the `live-test/` runner, Vagrant/Docker, and the CI workflow fork-scoped (branch-scoped trigger or an `if: github.repository == '<fork>'` guard) until upstream asks for them. This scoping is narrower than ARCHITECTURE.md's current Review Story, which describes the PR as including the `live-test/` runner, scripts, assertions, and artifacts; Phase 7 (which already touches ARCHITECTURE.md for its example-script path update, see that phase) updates the Review Story section to restate the split-PR strategy (Phases 1-4 upstream first, `live-test/` and CI following once asked for). Phase 8 adds further engine work outside this Phases-1-4 upstream scope (the run-N-ticks-then-pause option in `framework/options.cpp` and the relevant stage's entry point/update loop, e.g. `game/ui/tileview/cityview.cpp`, per the Determinism Contract); this is scoped as a planned second, small upstream PR once Phases 1-4 land, following the same merge-at-phase-boundary discipline, rather than left as unmanaged permanent fork divergence.

## Open Decisions (recommendations, not blockers)

- **Artifacts location**: `live-test/artifacts/<script-name>/` (per ARCHITECTURE.md's layout) is the canonical artifact location, superseding README's `build/tas/<script-name>/` spec and both docs' example scripts' hardcoded `build/tas/...` screenshot paths. Ownership is split by doc, not duplicated: Phase 5 updates README's Artifacts section (its run-directory spec and layout tree) and, separately, README's TAS Script section's example script path (that path lives in the TAS Script section, not the Artifacts section it names); Phase 7 updates ARCHITECTURE.md's example script's path (the one it converts into the first committed script). See those phases.
- **Docker vs Vagrant priority**: recommend Vagrant proves the environment first (Phase 5, matches the "Vagrant proves env first" pattern and the existing legacy Vagrantfile), then a Docker/container variant follows for local CI-parity use (Phase 8), built from the same shared provisioning script as the Vagrantfile and CI. GitHub Actions runs the smoke job on a bare `ubuntu-24.04` runner (same as the existing `cmake.yml` job) without a Docker layer; Phase 8's Docker variant is therefore compared against CI results, not against Vagrant, since CI is the environment it needs to reproduce.
- **result.json schema**: recommend a minimal v0 shape: `{name, status: pass|fail, exit_code, duration_ms, assertions: [{probe|artifact, expected, actual, pass}], probes: {log.warnings: N, ...}, artifacts: {screenshots: [...], log: path, save: path}}`. The added `probes` field is where `log.warnings` (and any other captured-but-non-fatal probe) is reported, since it is not itself an assertion; there is no separate `probes.json` file, superseding README's Artifacts listing, which names one (Phase 5 drops it from that listing). Extend only when a real script needs a new field.
- **"Nonblank" definition**: a screenshot is nonblank when the decoded image has at least N distinct pixel values and no single color covers 99% or more of the pixels (N to be picked when Phase 5 implements the check). This is the one definition used everywhere "nonblank" appears (whole-effort criteria, Phase 5, Phase 7).
- **Probe query grammar**: recommend dot-path only (`gamestate.player.balance`), no filters/indexing/wildcards in v1.
- **Protocol versioning**: `STATUS` reply includes an integer protocol version, implemented as a Phase 2 task (see Risks and Phase 2), not left as a future recommendation.
- **Save-fixture versioning**: recommend fixtures per test, regenerated by a scripted setup flow whenever the save format changes, rather than a central fixture-migration tool (built in Phase 8). Revisit if fixture count grows large.
- **Log-cleanliness definition**: recommend `log.errors == 0` as a hard assertion, included from Phase 5 onward; `log.warnings` is captured and reported in `result.json`'s `probes` field but non-fatal for v1. Revisit once the warning baseline is known.

## Reasoning Transparency

Alternatives considered and rejected:
- **Extend the prototype in place instead of layering first**: rejected because it directly violates the "refactor before extend" pattern and the preplanner's explicit MUST NOT (don't add commands/probes before the layers are split and the contract is locked). Extending first would bake more framework/forms violations into the design just as the layers are supposed to be separated out.
- **Thin `game/harness/` wrapper that still calls into `framework/harness.cpp` internals**: rejected because ARCHITECTURE.md is explicit that `framework/` must not parse high-level harness commands; a wrapper that just forwards to the old parser doesn't achieve the actual separation, only its appearance.
- **Docker-first for both local dev and CI**: rejected as the Phase 5/6 ordering because the stated pattern is "Vagrant proves env first, Docker follows as CI-friendly variant," and GitHub Actions already has a working bare-runner pattern in `cmake.yml` that's cheaper to extend than introducing a new container build in the same pass.
- **Full assertion DSL and full probe list before the first smoke test**: rejected per explicit MUST NOT; a bigger DSL/probe surface before proving the boot-to-MainMenu path adds untested surface area exactly where determinism is least proven.
- **A separate CI workflow for the smoke test instead of a `needs: build` job inside `cmake.yml`**: rejected because a separate workflow would multiply CI cost for no reason when the binary and `cd_minimal.iso` are already produced by the existing job; note that the chosen design is still a separate job (Phase 6), and `needs: build` only shares the compiled binary and the cached iso with the build job, not the checkout or dependency install, both of which the smoke job still performs itself on its own fresh runner (see Phase 6's step list).

What would have to be true for this plan to fail silently (unnamed assumptions):
- That `cd_minimal.iso` alone is sufficient to reach `MainMenu` deterministically: Phase 5's acceptance criterion (booting via `cd_minimal.iso` to MainMenu) verifies this directly, so it is no longer a silent-failure risk for MainMenu specifically; the same question for CityView-and-beyond content stays genuinely open and undiagnosed until Phase 8's entry gate (see Open Questions).
- That `Game.ASyncLoading=false` plus dummy audio/software GL fully removes timing races. If some other async path exists (e.g. background texture decode, worker threads not gated by that option), `log.errors == 0` and nonblank-screenshot checks could pass flakily rather than deterministically, and nobody would notice until CI is intermittently red.
- That the `Form`/`UI` class structure in `forms/` supports a single clean hook point. If it doesn't, Phase 3 could quietly re-grow into a scattered set of small hooks that functionally re-creates the command-logic-in-forms problem it's meant to remove.
- That GitHub Actions' bare `ubuntu-24.04` runner behaves close enough to the Vagrant Ubuntu 24.04 box (same Mesa/software-GL stack) that a Phase 5 local pass reliably predicts a Phase 6 CI pass. If not, "nonblank screenshot" could be flaky specifically in CI without ever reproducing locally.
- That forcing `OpenApoc.NewFeature.SeedRng=false` plus the default seed-0 rng state and its save-serialization round-trip gives enough determinism for Phase 5-7 scripts, and that `std::uniform_int_distribution`'s implementation-defined algorithm does not need to match across platforms for this plan's Linux-only CI/Vagrant targets. If a later Phase 8 script needs a fixed seed other than 0 (or ever needs to compare a Linux-generated result against a Windows one), that is new engine work outside this plan's scope, discovered late rather than flagged now.
- That `tests/test_harness.cpp`'s existing coverage can be ported 1:1 to the new grammar in Phase 2's `test_harness_protocol`. If the old tests are tightly coupled to `framework/harness.cpp` internals rather than to the command grammar itself, the port could silently under-cover the new parser while CTest still reports green.
- That duplicating the winsock includes/link onto `game/harness/`'s new CMake target in Phase 2, while leaving `framework/`'s copies untouched until Phase 4 removes them, is sufficient for AppVeyor to stay green at both phases. If MSVC's build picks up the socket headers differently than gcc did, or the fork-PR/branch-filter mechanism this plan relies on to get an AppVeyor build at all (see Risks) is misconfigured, Phase 2/3/4's "AppVeyor stays green" acceptance criteria are what would catch it, not a Linux-only local build.
